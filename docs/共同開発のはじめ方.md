# ビジカレを共同開発する — 準備の手順

本番・ステージング・各自の作業ブランチ、の3段構えにします。
作業は各自のブランチで並行して進められ、詰まるのは確認のときだけです。

---

## A. 二宮さんの準備（一度だけ）

### 1. GitHub に共同開発者を招待する

リポジトリ `accel-business-college` の Settings → Collaborators →
Add people で、相手の GitHub アカウントを **Write** 権限で招待します。

### 2. Vercel に Viewer として招待する

Vercel の accelpartners チーム → Settings → Members → Invite。
ロールは **Viewer** を選びます。Viewer は追加費用がかからず、
プレビューやステージングの画面を見ることができます（デプロイはできません）。

デプロイは GitHub への push で自動的に走るので、Viewer で足ります。

### 3. ステージング用のブランチとURLを作る

```bash
cd ~/accel-business-college
git checkout -b staging
git push -u origin staging
git checkout main
```

Vercel の accel-business-college → Settings → Domains で
`stg.college.accel-dash.com` を追加し、**Git Branch を `staging`** に設定します。
accel-dash.com は Vercel 側で管理されているので、DNS の手作業は要りません。

### 4. ステージング用の環境変数を入れる

Vercel の Settings → Environment Variables で、**Preview** 環境にも
本番と同じ変数を入れます（値はステージング用に差し替えるものもあります）。

| 変数 | ステージングでの値 |
| --- | --- |
| `NEXT_PUBLIC_APP_URL` | `https://stg.college.accel-dash.com` |
| `NEXT_PUBLIC_SUPABASE_URL` | ステージング用 Supabase の URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | ステージング用の anon key |
| `SUPABASE_SERVICE_ROLE_KEY` | ステージング用の service role key |
| `SESSION_SECRET` | 本番とは別の値を新しく作る |
| `SLACK_CLIENT_ID` / `SLACK_CLIENT_SECRET` / `SLACK_SIGNING_SECRET` | 本番と同じで可 |
| `SLACK_BOT_TOKEN` | 本番と同じで可（通知を飛ばしたくなければ空に） |
| `VIMEO_ACCESS_TOKEN` / `UNSPLASH_ACCESS_KEY` / `ANTHROPIC_API_KEY` | 本番と同じで可 |

### 5. ステージング用の Supabase を用意する

**本番のデータベースをステージングから触らせないでください。** 実在するメンバーの
個人情報が入っており、開発中の操作で壊すと元に戻せません。

Supabase で新しいプロジェクト（無料プランで可）を作り、
`supabase/schema.sql` と `supabase/*.sql` を順に実行してスキーマを作ります。
会員データは入れず、空のまま開発用のダミーを少しだけ入れる形にします。

> 無料プランは1週間アクセスが無いと自動で停止します。開発中は問題になりませんが、
> 止まっていたら Supabase の画面から再開してください。

### 6. Slack アプリにステージングのURLを登録する

Slack の App 設定 → OAuth & Permissions → Redirect URLs に

```
https://stg.college.accel-dash.com/api/auth/slack/callback
```

を追加します。**これを入れないとステージングでログインできません。**

### 7. 秘密情報を渡す

`.env.local` の中身は、パスワードマネージャーの共有 Vault で渡してください。
**チャット・メール・Slack には貼らないでください。**

## B. 共同開発者の準備

```bash
git clone git@github.com:ninomiyalisting-glitch/accel-business-college.git
cd accel-business-college
npm install
```

受け取った内容で `.env.local` を作り、

```bash
npm run dev
```

で http://localhost:3000 が開けば準備完了です。

Claude で作業する場合は、このフォルダを接続してください。
`CLAUDE.md` に規約が書いてあるので、Claude はそれに従って動きます。

## C. 日々の流れ

1. 作業前に `git pull origin main`
2. 作業ブランチを切る（`feat/◯◯`）
3. 手元で `npm run dev` を見ながら直す
4. `npm run build` が通ることを確認
5. `staging` に push → https://stg.college.accel-dash.com で確認
6. プルリクエストを作る → 二宮がレビューして `main` にマージ（＝本番反映）

### プレビューURLについて

作業ブランチを push すると Vercel が自動でプレビューURLを作りますが、
**Slack ログインは通りません**。URLが毎回変わり、Slack アプリに登録された
リダイレクトURLと一致しないためです。

ログインが要らない画面（トップページ、`/welcome`）の確認にはプレビューが使えます。
ログインが要る画面は `staging` で確認してください。

### 衝突を避けるために

- 1つの作業は小さく区切り、ブランチを長く持たない
- 同じファイルを2人で同時に触らない（着手前にひと声かける）
- `staging` は共有です。誰かが確認中なら、順番を譲る

## D. やってはいけないこと

- `main` へ直接 push する
- 本番のデータベースに、確認せずに SQL を流す
- `.env.local` や鍵をコミットする
- `SUPABASE_SERVICE_ROLE_KEY` をクライアント側のコードで使う
- メンバーに通知が飛ぶ変更を、相談なしに本番へ出す
